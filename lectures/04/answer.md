## 宿題

- 取り組んだレベル：発展
- やったこと：SWE-bench Verified（https://huggingface.co/datasets/princeton-nlp/SWE-bench_Verified ）を選んだ。Hugging Face の Dataset Viewer で 500 件の難易度とリポジトリの内訳を見て、難易度の 4 段階から 1 件ずつ、計 4 件の問題（issue の文章・正解のパッチ・判定に使うテスト）を読んだ。作成の手順は、元の SWE-bench の論文（arXiv 2310.06770）、公式ページ（https://www.swebench.com/verified.html ）、OpenAI のブログ「Introducing SWE-bench Verified」（2024-08-13）と「Why we no longer evaluate SWE-bench Verified」（2026-02-23）で調べた
- 結果：

  **データセットの中身**

  - 1 件は「GitHub の実際の issue の文章 ＋ 修正前のリポジトリ」。モデルはリポジトリを書き換えるパッチを出す。12 の有名な Python リポジトリから集めてあり、500 件のうち django が 231 件（46%）、sympy が 75 件、sphinx が 44 件と偏っている
  - 難易度：各問題の `difficulty` 列に、4 段階の値が入っている。Verified を作るときに、確認役の開発者が「経験のある開発者がこの issue を直すのに、どのくらい時間がかかるか」を見積もって付けたもの
    - 件数と、正解パッチで変わった行数の中央値は、次のとおり

      | 難易度 | 件数 | 変わった行数（中央値） |
      |---|---|---|
      | 15 分未満 | 194 件 | 5 行 |
      | 15 分〜1 時間 | 261 件 | 10 行 |
      | 1〜4 時間 | 42 件 | 35.5 行 |
      | 4 時間超 | 3 件 | 124 行 |

    - 測っているのは「人が直すのにかかる時間」で、LLM にとっての難しさではない。モデルの正答率から決めた値でもない
    - 時間には、修正を書く時間だけでなく、コードを読んで直す場所を探す時間も含まれる。そのため、変わる行数とは必ずしも比例しない。たとえば下の django-12708 は「1〜4 時間」だが、修正は実質 1 行で、時間の大半は原因を突き止めるためにかかる
    - 件数は大きく偏っている（1 時間以内の問題が 9 割、4 時間超は 3 件だけ）。ほとんどが小さな修正で、Verified の正答率は、主に 1 時間以内で直せる問題での成績を表している

  **読んだ問題（要約）**

  表の「難易度」は、上の `difficulty` 列の値。読む問題は、4 段階から 1 件ずつ選んだ。

  | 難易度 | 問題 | 正解の修正 | 自分なら解けるか／LLM にとって何が難しいか |
  |---|---|---|---|
  | 15 分未満 | django-15930：`Case(When(~Q(pk__in=[]), ...))` で、生成される SQL が `CASE WHEN THEN ...` と条件の抜けた形になり、構文エラーになる | 1 ファイル 5 行。「全件に当てはまる条件」は空の SQL に変換されるので、`CASE WHEN` の中で空なら常に真の条件に置き換える | 原因の当たりは付くが、巨大な django のどこを直すかを探すのに時間がかかる。修正は小さく、難しいのは「空の条件が空文字列になる」という内部の約束を知っていることと、直す場所を探すこと |
  | 15 分〜1 時間 | sympy-18211：方程式を `as_set()` で集合にしようとすると `NotImplementedError` で落ちる。解けないなら「条件付きの集合（ConditionSet）」を返してほしい | 1 ファイル。例外を捕まえて ConditionSet を返す | issue には `solveset` と書いてあるが、直すのは `relational.py` で、issue の言葉どおりに探すと迷う。issue のスレッドのヒント欄には、ほぼ正解のパッチが書かれていた |
  | 1〜4 時間 | django-12708：同じフィールドに `unique_together` と `index_together` があるとき、`index_together` を消すマイグレーションが「制約が 2 つ見つかった」で落ちる | 1 ファイル。消すインデックスを探す条件に「unique ではないもの」を足すだけ | 修正は実質 1 行だが、スキーマ編集とデータベースの制約の調べ方を理解しないと正しい場所に行き着けない。issue は 2 つの論点（消せない／宣言を移すと作り直される）を挙げているが、テストが見るのは 1 つ目だけ |
  | 4 時間超 | sphinx-7590：C++ のユーザー定義リテラル（`1.0q_J` のような単位付きの数値）を、Sphinx の C++ ドキュメント機能が解釈できず警告が出る | 3 ファイル 232 行。C++ の構文解析器にリテラルの規則を足す | 自分では解けない。C++ の文法の知識と大きな構文解析器の読解が要る。判定のテストは出力の文字列を細かく照合するので、方針が正しくても書き方が違うと落ちうる |

  **作成の人数と手順**

  1. 元の SWE-bench（2023 年、論文の著者はプリンストン大などの研究者 7 名）：12 リポジトリの約 9 万件のプルリクエストから、①issue を解決していて、②テストを追加・変更しているものを選び、③そのテストが「修正前は失敗、修正後は成功」になり、環境構築でエラーが出ないものだけを残して 2,294 件にした。問題文は人が新しく書いたのではなく、OSS の開発者が実際に書いた issue そのもの
  2. Verified（2024 年、OpenAI と SWE-bench の作者）：元のテストセットから無作為に 1,699 件を選び、93 人の経験ある Python 開発者が 1 件につき 3 人ずつ独立に確認した。見たのは「issue の説明が不十分ではないか」「判定のテストが、正しい解答まで不合格にしていないか」などで、それぞれを 0〜3 の深刻度で付ける。3 人のうち最も厳しい判定を採り、2 以上が付いた問題は落とした。残った中から 500 件を Verified にした（1,699 件のうち 3 割弱しか残っていない）。難易度（直すのにかかる時間）の見積もりもこのとき付けた
  3. 採点：モデルのパッチを Docker 環境で当て、`FAIL_TO_PASS`（修正前は失敗していたテスト。成功すれば issue を直せた）と `PASS_TO_PASS`（元から通っていたテスト。壊していないかを見る。上の例では 1 件につき 24〜101 個）の全部が通れば解決とする。LLM も人も採点に入らない
  4. その後：OpenAI は 2026-02-23 に、Verified のスコアの報告をやめると発表した。モデルがよく失敗する問題を監査すると、少なくとも 59.4% のテストに欠陥があり（issue に書かれていない機能や関数名を要求するなど）、正しい解答を落としていた。また問題と正解のパッチは公開の GitHub にあるので学習データに入り、最近のモデルは正解のパッチを記憶から再現できたという。代わりに SWE-bench Pro を勧めている

  **第4回の評価セットとの違い**

  | | 第4回の評価セット | SWE-bench Verified |
  |---|---|---|
  | 件数 | 10 件 | 500 件（2,294 件 → 1,699 件を確認 → 500 件） |
  | 誰が作ったか | 講師 1 人が質問を作り、回答は第3回のエージェントが生成 | 問題文は OSS の開発者が実際に書いた issue。93 人が 1 件につき 3 人で確認 |
  | 何を測るか | 指示（INSTRUCTIONS）どおりにふるまえるか。断る・ヒントに留めるなど、能力より「ふるまい」 | 実際のバグを直せるか。純粋な能力 |
  | 問題の選び方 | エッジケースを意図して層化（表記ゆれ・講座外・指示を無視して など） | 実際の issue をそのまま使い、難易度は事後に見積もる。易しい問題と django に偏っている |
  | 採点 | 人と LLM がルーブリックで T/F/unsure を付ける。「回の表示」だけコード | テストの実行だけで、決定的に判定。主観の基準はない |
  | 採点器の検証 | 人のラベルと LLM の判定の一致率を見る | 人がテストの妥当性を確認する（それでも欠陥が残っていた） |
  | 曖昧な問題の扱い | 基準に方針を書き足して決める（STEP 3） | 問題ごと落とす |
  | 漏洩 | 公開されておらず、学習データに入る心配はほぼない | 公開リポジトリが元なので、学習データに入っている |

- 気づき・疑問：
  - テストで機械的に採点すれば「採点器を信じてよいか」の問題はなくなると思っていたが、そうではなかった。第4回の演習では LLM の判定を人のラベルと比べて信頼性を確かめたが、Verified はそれをテストに対して 93 人規模で行っていた。それでも 2 年後に、監査した問題の 59.4% でテストに欠陥が見つかっている。コードで判定する基準も、判定そのものが正しいかを人が確かめる必要がある
  - 曖昧な問題への対処が対照的だった。第4回の演習では unsure を「基準で決めていない論点」として基準に方針を書き足したが、Verified は説明が不十分な問題をデータから落としている。落とすと評価はきれいになるが、「曖昧な依頼にどう対処するか」という実務で大事な力は測れなくなる。第4回の評価セットの #05（用語集にない語）や #09（空の質問）のような問題は、Verified では落とされる側だと思う
  - 3 人のうち「最も厳しい判定」を採るのは、一致率を見る第4回のやり方とは別の考え方だった。見逃しを減らすために、多く落とすことを受け入れている。3 人の判定がどのくらい一致していたかは、今回調べた範囲では分からなかった
  - 難易度は「人が直すのにかかる時間」で、LLM にとっての難しさとは別物だと感じた。sympy-18211 のように、修正は短いのに issue の言葉が直す場所とずれている問題は、人よりも LLM の方が迷いそうに思う
  - 公開データで作ったベンチマークは、時間がたつと学習データに入ってしまう。第4回の評価セット（10 件）のように非公開の小さな評価セットを自分で持っておくことには、数が少なくても意味がある
  - 補足：OpenAI のブログは自動取得が拒否されて直接読めなかった。93 人・1,699 件・3 人ずつ・0〜3 の深刻度・2026 年の発表の数字は、検索結果と二次記事（DEV Community、THE DECODER）で確かめたもの。元の SWE-bench の手順は論文の本文で、件数と難易度の内訳は Hugging Face のデータで確かめた
